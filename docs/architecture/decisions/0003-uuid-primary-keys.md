# ADR-0003 — UUIDv4 primary keys + separate human-readable numbers

**Status:** Accepted · 2026-08-17

## Context

Plan §47 requires "UUIDs or a documented ID strategy". IDs appear in URLs the customer sees, in POS
requests, and in future offline-generated records.

## Decision

- Every domain table uses `UUIDField(primary_key=True, default=uuid4, editable=False)`.
- Human-facing identifiers are separate columns generated by `core.services.next_number()`:
  `RGN-WEB-000123`, `RGN-POS-000456`, `PO-000012`, `RET-000007`.
- `next_number()` uses a `NumberSequence` row locked with `select_for_update()` — never `count() + 1`,
  which double-issues under concurrency.

## Consequences

- No enumeration of orders/customers by incrementing an integer in a URL.
- Offline POS (V2) can mint ids client-side without collisions.
- Slightly larger indexes and non-sequential inserts. Accepted at this data volume; the ledger and order
  tables are additionally indexed on `(branch, created_at)` which is how they are actually queried.
- Human references stay short and speakable on the phone — a UUID is unusable at a counter.
